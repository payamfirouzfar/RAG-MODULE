# RAG-MODULE v0.1 Architecture Specification

Status: proposed foundation for Step 5

This document defines the architecture we build toward before adding real RAG providers, storage backends, or model integrations.

## 1. Product definition

RAG-MODULE is an open-source framework kernel for designing, composing, executing, evaluating, observing, and replacing RAG architectures.

The framework must let a developer build a new architecture without modifying the core. Examples include Basic RAG, Hybrid RAG, Graph RAG, Multimodal RAG, Agentic RAG, and research prototypes.

The core is not a provider SDK, vector database wrapper, or copy of PyTorch/Haystack/LlamaIndex. PyTorch-inspired composability and inspection are retained where useful, but RAG-MODULE owns its own contracts and execution semantics.

## 2. Architectural layers

```text
User Architecture
      |
      v
Components -> Blocks -> Graph/Architecture
      |
      v
Runtime + Execution Policies
      |
      +---- Observability
      +---- Evaluation
      +---- Resource lifecycle
      +---- Provider routing
      |
      v
Optional plugins/providers
```

### Component

The smallest reusable unit of behavior. A component has a stable contract, typed input/output boundaries, lifecycle semantics, capabilities, and replaceable implementation.

Examples: Retriever, Generator, Embedder, Reranker, Chunker, Router, Parser, Fusion, Validator.

### Block

A reusable composition of components. A block is itself composable and must not require special runtime treatment.

Examples: RetrievalBlock, ReasoningBlock, MultimodalBlock.

### Architecture

A complete RAG design composed from components and blocks. Architectures are user-defined and must not require changes to core.

### Runtime

Executes an architecture and owns execution identity, scheduling semantics, lifecycle, error propagation, policies, and observability integration. Runtime behavior must remain separate from component business logic.

## 3. Component contract

The existing `Module` is the Step 1-4 implementation primitive. We will not delete it. Step 6 introduces `Component` (`ragtorch.core.component.Component`, ADR-010): a minimal, `@runtime_checkable` structural `Protocol` with exactly `name`, `component_type`, and `__call__(input, *, context=None)`.

`Component` is the stable *conceptual* contract; `Module` remains the concrete *implementation* primitive. The relationship is structural, not inheritance-based:

```text
                 Component (Protocol)
                        ▲
                        │  structural — no inheritance required
                        │
                     Module
                        ▲
                 ┌──────┴──────┐
                 │             │
            RAGModule      Sequential
```

`Module` gained two properties (`name` returning the existing `_name`,
`component_type` returning `type(self).__name__`) and now structurally
satisfies `Component` with zero migration: every existing `Module`
subclass, including every one already in the test suite, satisfies the
protocol without inheriting from it or changing any call site. An
independent, non-`Module` class implementing the same three members also
satisfies `Component` — this is the entire point of using a `Protocol`:
a future `Retriever`, `Generator`, `Embedder`, or `Reranker` can be
recognized by the framework without importing `ragtorch.core.Module` or
any `ragtorch` base class at all.

Migration rule:

- existing `Module` remains backward compatible;
- new contracts are introduced beside it;
- behavior is migrated only after contract tests exist;
- `RAGModule` must eventually represent a complete RAG architecture rather than merely being a marker subclass;
- no rename of `ragtorch` or package paths happens until the public contract is stable.

For Step 6, a component exposes only:

```text
name
component_type
__call__(input, *, context=None)
```

`configuration` and `capabilities` were deliberately excluded from this
step (see ADR-010 Alternatives considered) — no real component exists
yet to prove what shape either should take, and committing to fields
nothing needs yet works against the "small, stable interface" principle
(ADR-001). Both remain natural, additive extensions once a real component
exists.

`component_type` is currently `type(self).__name__` — descriptive
identity for humans and tooling, not yet a stable serialization
identifier (see ADR-010). A `Component` conformance check
(`isinstance(x, Component)`) has real, measured cost and must never
appear on a hot execution path (`Module.__call__`, `ExecutionEngine.execute`,
`Sequential.forward`); it belongs at explicit boundaries — registration,
tests, developer tooling — where it runs once per component instance,
not once per call.

Ports and typed I/O contracts are introduced only after the compatibility boundary is specified.

## 4. Composition model

The first composition primitive remains sequential execution. Future primitives are:

- Sequential
- Parallel
- Conditional
- Router
- Loop
- Graph/DAG

Graph scheduling, concurrency, and distributed execution are explicitly not part of the first Component migration.

Composition must be recursive: a Block can contain Components, a Block can contain other Blocks, and an Architecture can contain both.

## 5. Execution identity

`ExecutionContext` remains the explicit transport for run identity. No implicit current execution, thread-local execution, or context-global execution state is introduced.

Every nested execution must preserve:

- root run identity;
- parent-child relationship;
- immutable metadata;
- sibling isolation.

The existing Step 4 context propagation is retained as the compatibility baseline.

## 6. Observability contract

Observability is a framework capability, not a vendor dependency.

The kernel owns semantic events, while adapters may export them to logging, metrics, or OpenTelemetry later.

Events must be attributable to an execution. In particular, module lifecycle events must carry execution identity when a context exists. This closes a current gap: the event payload presently identifies only a module name, which is insufficient to distinguish concurrent or nested runs.

Observability must never become a hidden source of execution state.

Levels remain:

```text
OFF -> BASIC -> DEBUG
```

Nested trace spans and per-component metrics are a separate step after the Component/runtime contract is stable.

## 7. Evaluation contract

Evaluation is a first-class subsystem and must not depend on an LLM provider.

Two layers remain separate:

1. Framework correctness: contracts, unit tests, integration tests, failure behavior, compatibility, and performance.
2. RAG behavior: retrieval quality, generation quality, faithfulness, relevance, latency, cost, reliability, and routing/fallback quality once those capabilities exist.

Every major architectural feature ships with deterministic evaluation and a benchmark baseline.

## 8. Provider architecture

Providers are adapters, never the foundation of core.

Conceptually:

```text
Stable contract
    |
    +-- Ollama adapter
    +-- vLLM adapter
    +-- Hugging Face adapter
    +-- cloud provider adapters
```

The same rule applies to storage, graph databases, observability exporters, and other integrations.

Default installation remains local-first and dependency-light. Vendor-specific dependencies remain optional extras.

## 9. Provider routing and fallback

Provider selection becomes a first-class policy, not hidden exception handling.

Future routing must distinguish at least:

- unavailable provider;
- timeout;
- rate limit;
- resource failure;
- invalid output;
- quality-gate failure.

Fallback may be constrained by policy, including local-only operation. A quality-gated fallback may evaluate the primary result and escalate to another provider/model when the result does not meet the configured threshold.

This is intentionally future work; no provider router is implemented in this step.

## 10. Architecture inspection

The current `inspect()` API is retained as a compatibility surface. Internally, inspection will evolve toward a structured architecture snapshot containing:

- nodes;
- edges;
- component type;
- ports;
- configuration metadata safe for inspection;
- capabilities;
- package/version information.

Text, JSON, Mermaid, and other renderers should consume the same snapshot rather than maintaining separate graph representations.

## 11. Reproducibility

A run must eventually be attributable to:

- run ID;
- architecture/version;
- package version;
- source revision when available;
- configuration hash;
- provider/model identifiers;
- dataset/evaluation version;
- random seed where applicable.

Secrets are never included in architecture snapshots or run artifacts.

## 12. Security and data locality

Core must not silently persist sensitive input/output data. Local-only policies must be enforceable. Remote provider use must be explicit and observable.

API keys and secrets are configuration inputs, not architecture state.

## 13. Public API boundary

Anything re-exported from `ragtorch` or a documented public subpackage is public. Internal implementation modules remain private and may change.

**Update (Step 28, superseding the original text below):** the PyPI distribution name is `ragmodel` (`pip install ragmodel`) while the Python import name remains `ragtorch` (`import ragtorch`) — a permanent, deliberate split, not the full `ragtorch` → `ragmodule` rename originally anticipated here. The Python import name was never renamed and there is no plan to rename it; only the PyPI-facing distribution metadata changed. See [ADR-024](decisions/ADR-024-versioning-and-release-policy.md) and `evaluation/step28-evaluation.md` (28R) for the full decision record.

*Original text, preserved for history:* the package rename from `ragtorch` to `ragmodule` is deferred until the API boundary is stable. Backward compatibility takes priority over cosmetic renaming.

## 14. Step 5 acceptance criteria

Step 5 is complete when:

- this architecture is documented and reviewed against the current repository;
- current public APIs and requirements are explicitly mapped to the target architecture;
- the event execution-identity gap is closed by tests and implementation;
- no existing Step 1-4 behavior regresses;
- a new Component abstraction has a written contract and contract tests before implementation;
- performance and evaluation baselines are recorded;
- CI validates formatting, linting, typing, tests, evaluation smoke tests, and package build.

## 15. Explicit non-goals for Step 5

Do not implement yet:

- LLM integrations;
- embedding providers;
- vector databases;
- graph databases;
- automatic model fallback;
- quality-gated routing;
- parallel/distributed graph execution;
- OpenTelemetry exporter packages;
- cloud dashboards;
- a package rename;
- a giant inheritance hierarchy.
